# Домашняя работа 2 — MongoDB

## Запуск

Сначала нужно запустить Docker и открыть терминал в папке проекта.

```sh
docker compose up -d
```

Проверить состояние контейнеров можно командой:

```sh
docker compose ps
```

Для загрузки исходного набора данных используется:

```sh
docker compose run --rm lab reset
```

Посмотреть подготовленные данные, параметры запросов и ожидаемые ответы можно так:

```sh
docker compose run --rm lab fixtures
```

Основные проверки запускаются отдельно:

```sh
docker compose run --rm lab data
docker compose run --rm lab index
docker compose run --rm lab purchase
docker compose run --rm lab failover
```

Все четыре сценария последовательно запускаются одной командой:

```sh
docker compose run --rm lab all
```

Для ручной работы с базой можно открыть `mongosh`:

```sh
docker compose run --rm lab shell
```

## Данные и валидатор

У товара варианты размера и остатки лежат прямо в массиве `variants`. Для `products` добавлен
валидатор, который обязательные поля, типы данных, цену и остатки. Цена должна быть
`Decimal128` и не может быть отрицательной, остаток должен быть неотрицательным целым числом.

Также проверяется, чтобы у одного товара не было двух вариантов с одинаковым размером. Для этого
длина массива вариантов сравнивается с количеством уникальных значений `size`.

Позиции хранятся внутри заказа, потому что они всегда относятся к конкретной покупке и обычно
читаются вместе с ней. Сами заказы хранятся отдельными документами: история пользователя может
постоянно расти, поэтому складывать её в один большой документ было бы неудобно.

Цена в позиции заказа сохраняется та, которая была в момент покупки, чтобы изменение цен в
`products` не меняло цены товаров в старых заказах.

## Поиск товаров и история заказов

Для поиска используется `$elemMatch`:

```javascript
variants: {
  $elemMatch: {
    size, stock
  :
    {
      $gte: qty
    }
  }
}
```

Размер и остаток проверяются у одного и того же элемента массива при помощи `$elemMatch`, без него
Монго могла бы найти нужный размер у одного варианта, а достаточный остаток у другого.

Результат сортируется по `_id` по возрастанию. При этом когда у
A размер L имел остаток 0, то товар не попадал в поиск двух единиц. После изменения остатка на 2
товар
появился в результате.

История фильтруется по `userId` и `status`, сортируется сначала по дате от новых заказов к старым, а
при одинаковой дате — по `_id` по возрастанию. После этого берутся первые 20 документов.
Дополнительная сортировка по `_id` нужна, чтобы при одинаковых датах порядок всегда был одинаковым.

## Отчёт по продажам

Отчёт сделан полностью через aggregation pipeline:

1. Остаются только заказы со статусом `paid` за период `[from, to)`.
2. Массив `items` разворачивается через `$unwind`.
3. Позиции группируются по SKU, для них считаются количество и выручка.
4. Через `$lookup` подставляется название товара из `products`.
5. Результат сортируется по выручке, затем по SKU; остаются первые пять строк.

Выручка считается по цене из заказа, а не по текущей цене из `products`:

```text
revenue = сумма(qty × items.price)
```

Например, товар A встречается как 2 штуки по 100.00 и 1 штука по 120.00:

```text
Количество: 2 + 1 = 3
Выручка: 2 × 100.00 + 1 × 120.00 = 320.00
```

Получился такой топ:

| SKU | Товар     | Количество | Выручка |
|-----|-----------|-----------:|--------:|
| A   | Футболка  |          3 |  320.00 |
| B   | Рубашка   |          4 |  320.00 |
| C   | Толстовка |          3 |  270.00 |
| D   | Ремень    |          2 |  240.00 |
| E   | Сумка     |          1 |  200.00 |

После изменения текущей цены A на 999.00 отчёт не изменился, потому что в расчёте используются
сохранённые цены заказов.

## Индекс

Для истории заказов создан индекс:

```javascript
{
  userId: 1, status
:
  1, createdAt
:
  -1, _id
:
  1
}
```

Сначала идут поля, по которым используется точное равенство, затем поля сортировки для соответствия
ESR. `hint` не использовался, Моного сама выбрала новый индекс.

Результаты `explain("executionStats")` на 10 000 заказах:

| Вариант       | nReturned | totalKeysExamined | totalDocsExamined | Отдельная сортировка |
|---------------|----------:|------------------:|------------------:|----------------------|
| До индекса    |        20 |                 0 |             10000 | да                   |
| После индекса |        20 |                20 |                20 | нет                  |

До создания индекса был полный просмотр коллекции (`COLLSCAN`) и отдельная сортировка. После
создания индекса Монго использовала `IXSCAN`, прочитала 20 ключей и 20 документов. Результаты и их
порядок при этом не изменились.

Минус индекса в том, что он занимает место и его нужно обновлять при записи. То есть чтение
становится быстрее, но вставки и изменения получают небольшую дополнительную нагрузку.

## Покупка и транзакция

Списание остатков двух товаров и создание заказа выполняются в одной транзакции. Для неё
используются:

```javascript
readConcern: {
  level: "snapshot"
}
writeConcern: {
  w: "majority", j
:
  true, wtimeout
:
  10000
}
readPreference: "primary"
```

Сначала проверяется, есть ли уже заказ с таким `operationId`. Если его нет, для каждой позиции
выполняется условный `updateOne`. В условие входят SKU, размер и проверка `stock >= qty`. Остаток
уменьшается через `$inc`. Если хотя бы одна позиция недоступна, выбрасывается `ITEM_UNAVAILABLE`, и
транзакция откатывается.

Если оба списания прошли, создаётся заказ со статусом `created`, текущей датой и ценами из
`products`.
Выход из функции без ошибки приводит к commit, исключение к abort.

В проверке не хватало второго товара. Первое обновление A успело выполниться внутри транзакции
(`matched: 1`, `modified: 1`), но второе не нашло достаточного остатка. После abort остатки
полностью вернулись в исходное состояние, заказ не появился.

Для успешной покупки остаток A/M изменился с 10 до 8, B/L с 5 до 4, после чего появился один заказ
`purchase-001`.

Счётчики транзакций получились такими:

| Сценарий                  | started | committed | aborted |
|---------------------------|--------:|----------:|--------:|
| Не хватило второго товара |       1 |         0 |       1 |
| Успешная покупка          |       1 |         1 |       0 |

Транзакция отвечает за атомарность, но сама по себе она не защищает от повторной отправки уже
завершённого запроса. Для этого
используется `operationId`.

Если повторно приходит тот же `operationId` и те же параметры, возвращается сохранённый заказ без
нового списания. Сравниваются `userId`, `sku`, `size` и `qty`; текущая цена из `products` не
сравнивается. Если с тем же `operationId` приходит другое количество или другой состав позиций,
возвращается `REQUEST_CONFLICT`.

## Смена primary

Пробная запись выполняется через `updateOne` с `upsert` и `writeConcern: {w: "majority", j: true}`.
`upsert` нужен, чтобы повтор после временной ошибки соединения был безопасным.

В сохранённом прогоне до `stepDown` primary был `m1:27017`, а узлы `m2:27017` и `m3:27017` были
secondary. После переключения `m1:27017` стал secondary, новым primary стал `m2:27017`, а роль
`m3:27017` не изменилась. Старый документ `before` успешно прочитался, новая запись `after` прошла с
`acknowledged: true`, и в конце в коллекции находились оба
документа.

Это работает потому, что клиент подключён к replica set через список начальных адресов, а не к
одному конкретному серверу. Он получает информацию о ролях узлов и после выборов начинает отправлять
записи новому primary.

Подтверждение `majority` означает, что запись получили большинство голосующих узлов. Но это не
гарантирует, что любая secondary уже успела применить её у себя. Поэтому чтение с отстающей
secondary сразу после записи может вернуть старые данные.

## Шардирование

В задании `orders` распределена по ключу `{userId: 1}`.

Для истории пользователя с `userId: 2500` будет опрошен только шард B, потому что значение 2500
попадает в его диапазон `[2000, 5000)`. Это targeted query, т.к в фильтре есть точное значение ключа
шардирования.

В общем отчёте фильтр идёт только по `status: "paid"`, а `userId` отсутствует. Поэтому `mongos` не
может выбрать один диапазон и отправит запрос на оба шарда A и B. Потом результаты будут объединены.

Индекс `{status: 1}` не уменьшит количество шардов во втором запросе, их в любом случае будет 2. Он
может ускорить поиск оплаченных заказов внутри каждого шарда, но на маршрутизацию не повлияет,
потому
что `status` не входит в ключ шардирования.
